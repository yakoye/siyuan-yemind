# YeMind 文档分类与时间命名设计

> 状态：已确认
>
> 设计时间：2026-07-29 19:14（Asia/Shanghai）
> 适用范围：`siyuan-yemind/docs/`

## 1. 目标

当前文档同时混用中文、英文、版本号、日期和无日期命名，设计、计划、验证、验收与历史构建资料交叉堆放，查找困难。此次整理需要达到以下结果：

1. 长期维护的规范文件拥有稳定路径，不因每次修改而改变链接。
2. 设计、实施计划、验证、验收和回归记录可以根据文件名直接识别产生时间、版本和主题。
3. 历史文档分类归档，但不删除、不合并、不改写历史结论。
4. 仓库内引用同步迁移，整理后不存在指向旧路径的失效链接。
5. 新增自动检查，避免后续重新产生命名混乱。

## 2. 命名原则

### 2.1 稳定基准文档

长期维护、始终只有一个现行版本的文档不增加日期或版本号，采用简明中文名称：

```text
docs/standards/回归验收清单.md
docs/standards/开发要求.md
docs/standards/测试与验收.md
docs/standards/版本管理.md
docs/standards/版本与发布规范.md
```

稳定基准文档修改后仍保留原路径。历史变化由 Git 记录，不复制成多个带日期版本。

### 2.2 历史文档

设计、计划和执行证据统一采用北京时间，精确到分钟：

```text
YYYY-MM-DD-HHmm-版本-主题-文档类型.md
```

示例：

```text
2026-07-29-1914-v1.5.1-基础编辑事务-设计.md
2026-07-29-1930-v1.5.1-基础编辑事务-实施计划.md
2026-07-29-2215-v1.5.1-基础编辑事务-验证记录.md
```

没有正式版本号的开发候选记录使用 `dev`：

```text
2026-07-29-1915-dev-文档分类与时间命名-设计.md
```

文件名约束：

- 日期和时间固定使用数字格式 `YYYY-MM-DD-HHmm`。
- 时间解释为 `Asia/Shanghai`，文件名不再重复写时区。
- 版本统一使用 `vX.Y.Z`；无正式版本使用 `dev`。
- 主题使用简短中文或项目已有的固定专名。
- 文档类型固定为 `设计`、`实施计划`、`测试用例`、`验证记录`、`验收记录`、`回归记录`、`构建清单`之一。
- 文件名不使用空格、括号或多个连续连接符。

### 2.3 非文档资产

示例文件、主题颜色数据、构建输入 Source Map 等不是阅读型历史文档，不强制增加时间：

```text
docs/examples/
docs/theme-colors/
docs/build-input/
```

离线构建清单属于构建证据，需要归入对应历史版本并增加生成时间。

## 3. 目录结构

整理后的目标结构：

```text
docs/
├─ README.md
├─ standards/
├─ designs/
├─ plans/
├─ releases/
│  └─ vX.Y.Z/
├─ regression-runs/
├─ archive/
│  └─ v0.9/
│     ├─ designs/
│     ├─ boundaries/
│     ├─ test-matrices/
│     ├─ verifications/
│     └─ manifests/
├─ ai/
├─ examples/
├─ theme-colors/
└─ build-input/
```

目录职责：

- `standards/`：唯一现行基准。
- `designs/`：当前主线和仍具参考价值的设计。
- `plans/`：当前主线实施计划。
- `releases/vX.Y.Z/`：正式版本的测试、验证和验收证据。
- `regression-runs/`：未必对应正式发版的独立回归执行记录。
- `archive/v0.9/`：早期版本产生的大量英文设计、产品边界、测试矩阵、验证和离线构建清单。
- 资源型目录保持原职责。

原工作流目录中的历史设计与计划分别迁移到 `docs/designs/` 和 `docs/plans/`。`docs/superpowers/` 只保留工作流说明或迁移说明，不继续作为项目文档入口。

## 4. 历史时间推导

旧文档时间按以下优先级确定：

1. 文件首次进入 Git 的提交时间。
2. 未跟踪文件使用文件创建时间。
3. 无可靠创建时间时使用最早可得的文件修改时间。
4. 仍无法判断时使用迁移时间，并在迁移清单的 `timeSource` 字段标记为 `migration`。

所有 Git 时间转换为 `Asia/Shanghai` 后再写入文件名。不得只根据文档正文中的日期猜测精确分钟。

迁移前生成机器可读清单：

```json
{
  "oldPath": "docs/releases/v1.0.0/2026-07-27-1110-v1.0.0-版本-验证记录.md",
  "newPath": "docs/releases/v1.0.0/2026-07-27-1432-v1.0.0-插件运行目录整理-验证记录.md",
  "timestamp": "2026-07-27T14:32:00+08:00",
  "timeSource": "git-first-add",
  "category": "release-verification"
}
```

迁移清单必须进入仓库，作为重命名审计和以后排查链接的依据。

## 5. 迁移策略

迁移分四批执行：

1. 建立 `docs/README.md`、目标目录和命名检查规则。
2. 迁移稳定基准文档并更新唯一正式路径声明。
3. 迁移当前版本设计、计划、测试、验证、验收和回归记录。
4. 迁移 v0.9 历史文档与离线构建清单。

每批都先生成旧路径到新路径的映射，再使用 Git 感知的重命名完成移动。不得先删除旧文件再创建新文件。

文档正文只允许修改：

- Markdown 相对链接；
- 明确写出的文件路径；
- “唯一正式路径”之类已经因迁移失效的说明；
- 文档索引和迁移说明。

历史结论、测试数字、发布日期、哈希和验收结论不得随整理而改写。

## 6. 链接和代码引用

迁移需要扫描并更新：

- `README.md`、`README_zh_CN.md` 和 `CHANGELOG.md`；
- `docs/**/*.md`、`docs/**/*.txt` 和文档型 JSON；
- `.github/**/*.yml`、`.github/**/*.yaml`；
- `package.json` 与构建、测试、发布脚本；
- 源码和测试中硬编码的文档路径。

相对链接按新文件所在目录重新计算。普通历史文字中出现的旧路径，如果用于描述当时的计划，也必须改成当前可访问的新路径，并可在括号中注明“原路径”。

## 7. 文档索引

`docs/README.md` 是唯一人工入口，包含：

1. 当前必读规范；
2. 当前正式版本的设计、测试、验证和验收；
3. 当前正在执行的设计与计划；
4. 最近回归记录；
5. 历史版本归档入口；
6. 命名规则和迁移清单入口。

索引不复制文档内容，只提供简短说明和链接。

## 8. 自动检查

新增只读检查脚本，并纳入 `npm run check` 或等价质量门禁。检查至少包括：

- 历史文档文件名符合时间、版本、主题和类型格式；
- 稳定基准文档没有日期或版本后缀；
- Markdown 本地链接目标存在；
- 仓库中不存在仍指向已迁移旧路径的有效引用；
- 同一分钟、同版本、同主题、同类型不会出现重名；
- 迁移清单中的新路径全部存在，旧路径全部不存在。

检查脚本不得自动改名，避免 CI 隐式修改仓库。

## 9. 错误处理与回滚

- 时间来源不明确：保留文件不动，记录到迁移报告，不能猜测。
- 新路径冲突：追加更具体的主题，不使用 `(1)` 或随机后缀。
- 链接无法自动判断：列入人工复核清单，完成前阻断迁移验收。
- 迁移中途失败：使用 Git 重命名记录恢复本批文件；不得使用破坏用户未提交修改的 `git reset --hard`。
- 当前工作区已有大量未提交代码修改，文档整理必须按明确文件清单操作，不能覆盖或提交无关修改。

## 10. 验收条件

整理完成必须满足：

1. `docs/README.md` 能访问全部现行规范、当前版本资料和历史归档。
2. 所有历史阅读型文档文件名包含精确到分钟的北京时间。
3. 稳定基准文档路径保持稳定且名称简洁。
4. Markdown 本地链接检查零错误。
5. 全仓库旧路径残留检查零错误，迁移说明中的审计字段除外。
6. 迁移清单覆盖所有被移动文件，且每项包含时间来源。
7. Git 能把绝大多数文件识别为 rename，而不是无关删除和新增。
8. 当前编辑器修复、构建产物和用户未提交修改不进入文档整理提交。
