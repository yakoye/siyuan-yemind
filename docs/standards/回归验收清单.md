# YeMind 累积式回归验收清单

> 文件名：`回归验收清单.md`
> 清单版本：`1.1`
> 唯一正式路径：`siyuan-yemind/docs/standards/回归验收清单.md`
> 适用范围：YeMind 思源插件版、独立网页版及二者共享核心代码
> 目的：保证每次开发是在现有稳定能力上继续累积，而不是“修好一个、改坏一个”
> 使用者：Codex、开发者、测试者、发布审查者

---

## 0. 使用规则

### 0.1 勾选标记

- `[ ]`：尚未执行。
- `[x]`：已经实际执行并通过，且有证据。
- `[!]`：执行失败，阻断合并或发布。
- `[-]`：本次确认不适用，必须写明原因。
- `[?]`：结果不确定，需要继续验证，不能视为通过。

### 0.2 不允许继承历史勾选结果

- [ ] 每次开发、合并或发布前，将本次需要执行的项目重新置为 `[ ]`。
- [ ] 不得因为旧版验收记录中曾经通过，就直接把本次标为 `[x]`。
- [ ] 自动测试通过数量、截图、构建产物和实机结果必须属于本次提交。
- [ ] `[-]` 必须写明不适用原因，不能用来跳过难测项目。
- [ ] 没有实际证据的项目不得标记为完成。

### 0.3 规则优先级

出现文档冲突时，按以下顺序处理：

1. 用户当前明确要求。
2. 最新真实浏览器与思源实机验证结论。
3. 当前版本测试用例和本文件。
4. 当前版本实施计划。
5. 早期版本计划和历史原型行为。

### 0.4 当前视觉冲突的统一结论

早期设计清单曾允许半透明、背景模糊和毛玻璃；后续 Version47 修复与实机验证已将右键菜单等操作面板改为平面不透明样式。以后统一执行：

- [ ] 菜单、右键菜单、搜索面板、主题面板、样式面板、导入导出面板、对话框、卡片面板和侧栏默认使用不透明实体背景。
- [ ] 不得擅自新增 `backdrop-filter`、背景模糊、毛玻璃或让正文从操作面板下方透出。
- [ ] 不得为了“现代感”降低面板、菜单或按钮可读性。
- [ ] 只有基线明确要求的非可见定位容器可以透明。
- [ ] 富文本浮动工具栏的纯定位外层可以透明；实际可见按钮组必须使用统一不透明实体承载层、无重阴影，正文不得从按钮或文字下方透出。
- [ ] “已保存”等静默状态可以没有实心底色，但必须保持文字、图标和焦点状态清晰。
- [ ] 任何透明度变化都必须提供修改前后截图和明确需求依据，否则视为视觉回归。

### 0.5 唯一基线与执行副本

- [ ] 本文件是 YeMind 回归规则的唯一正式基线；仓库外副本、旧版验收记录和聊天摘要不得作为平行规则源。
- [ ] 永久基线只维护规则，不直接保存某一次开发的 `[x]` 勾选结果。
- [ ] 每次开发或发布从本文件创建独立验收记录，文件名使用 `docs/regression-runs/YYYY-MM-DD-版本或候选版本-主题.md`。
- [ ] 独立验收记录必须写明基线清单版本、创建时的基线提交 SHA、候选提交 SHA 和执行档位。
- [ ] 基线后续变化不回写或篡改已归档的历史验收记录。

### 0.6 执行档位

| 档位 | 必须执行 | 适用场景 |
|---|---|---|
| `P0` | 第 4 节、定向失败测试、受影响区域最小实机验证 | 所有进入共享核心或正式构建的改动 |
| `影响域` | `P0` + 第 1.1 节勾选的全部影响域 + 相邻公共组件 | 日常功能开发、缺陷修复和界面调整 |
| `发布级` | `P0` + 全部适用自动门禁 + 双端实机 + 发布物与线上验证 | 版本号变更、Git 标签、GitHub Release 或正式 Pages 发布 |

- [ ] 执行档位只决定本次必须覆盖的范围，不得用来跳过已经确认受影响的项目。
- [ ] 同一改动跨越多个影响域时，执行范围取并集。
- [ ] 任何数据格式、存储、共享核心或公共组件变化，至少按“影响域”执行。
- [ ] 用户明确要求“全量测试”时直接使用“发布级”，不得降级。

### 0.7 稳定用例编号

- [ ] 新增或拆分的回归用例使用 `YM-<档位或领域>-<三位序号>`，例如 `YM-NODE-021`、`YM-OUTLINE-014`；示例不得占用尚未登记的正式编号。
- [ ] 已有无编号条目在被修改、失败或自动化覆盖时补充稳定编号，不因章节移动而改号。
- [ ] 自动测试、截图、trace、验收记录和缺陷报告优先引用稳定编号。
- [ ] 一个编号只描述一个可判定结果；不得把多个互不相关动作塞入同一编号。
- [ ] 删除用例时保留编号并记录弃用依据，不把旧编号分配给新语义。

## 2. 不可破坏的产品原则

- [ ] 新功能通过不等于版本通过。
- [ ] 本次需求、原有核心能力、视觉基线和双端一致性必须同时通过。
- [ ] 未明确要求的视觉变化一律视为回归，不视为主动优化。
- [ ] 未明确要求时不得更换字体、字号、字重、圆角、阴影、间距、颜色或组件层级。
- [ ] 不得用演示代码、固定示例数据或局部 React 状态替换真实业务能力。
- [ ] 所有可点击控件必须接入真实动作；未实现的能力必须隐藏或明确禁用。
- [ ] 不得顺手重构无关模块、升级无关依赖或修改无关页面。
- [ ] 不得用大量高优先级 CSS 覆盖掩盖旧规则冲突，应删除、合并或修正根因。
- [ ] 不得用固定长等待掩盖竞态，应等待明确 DOM、保存或渲染状态。
- [ ] 不得通过调用内部函数代替真实用户交互完成 E2E 验收。
- [ ] 共享核心变化必须同时验证思源插件版和独立网页版。
- [ ] 旧导图的 UID、结构、富文本、图片、附件和局部样式不得因为界面升级而丢失。
- [ ] 自动保存、手动保存、关闭前保存和快速连续写入不得相互覆盖。
- [ ] 任何可能删除或覆盖用户数据的同步、导入和迁移操作必须先验证目标路径和回滚方法。

### 2.1 同类组件继承与禁止重新发明

> 任何新增按钮、图标、菜单项、输入框、卡片、工具栏、弹出面板、对话框或窗口，都不是一个独立的视觉设计任务，而是现有组件家族中的一个新成员。默认要求是“找到最近的同类，继承完整规则，只修改需求明确要求的内容”。

复用优先级必须按以下顺序执行：

1. 直接复用已有组件和已有动作。
2. 在已有组件上增加受控 `variant`、配置项或插槽。
3. 确实无法直接复用时，复制最近同类的完整骨架、样式、交互、无障碍和测试契约后再改内容。
4. 只有没有任何同类组件可承载当前语义时才允许新建；新建前必须说明原因、影响面并获得明确批准。

- [ ] 开发前已找到“最近的同类参考组件”，并记录组件名、源码文件、运行位置和截图。
- [ ] 新增控件优先使用现有公共组件、公共 CSS 类、设计 token、图标注册表和交互控制器。
- [ ] 已存在同类组件时，不得重新编写一套新的 DOM、CSS、定位、动画、焦点或关闭逻辑。
- [ ] “添加一个按钮”默认表示复制同类按钮的完整结构和状态，只替换图标、文字、动作与必要的禁用条件。
- [ ] “添加一个图标”默认表示从统一图标注册表选择或按同一图标规范补充，不得临时绘制另一套尺寸、线宽或风格。
- [ ] “添加一个弹窗/对话框/面板”默认表示复用同类壳层、标题栏、关闭按钮、内边距、底部按钮区、层级、焦点和键盘行为。
- [ ] 只允许需求明确提出的差异；其余尺寸、圆角、边框、阴影、背景、字体、间距、动画、层级和交互必须与参考组件一致。
- [ ] 不得为一个新控件新增仅自己使用的字号、颜色、圆角、阴影、图标尺寸、行高或 `z-index`，除非设计系统中已有对应 token。
- [ ] 不得通过独立 `margin-left`、负边距、绝对坐标、额外透明度或高优先级 CSS 把新控件“修得看起来差不多”。
- [ ] 如果现有同类组件本身存在缺陷，应先确认是修复整个组件家族，还是只保持现状；不得只在新控件上做特殊补丁。
- [ ] 修改公共组件时，必须回归所有调用位置；增加 `variant` 时，必须证明默认 variant 的外观和行为没有变化。
- [ ] 新控件的结构、样式和行为差异必须在最终报告中逐项列出；未列出的差异视为非预期回归。
- [ ] 代码审查必须拒绝“功能相同但另起一套实现”的平行组件。
- [ ] 新增组件必须有同类对比截图和自动几何/样式断言；仅凭“看起来差不多”不得通过。

### 2.2 组件家族契约

每个组件家族至少要有一个正式基线：

- 按钮家族：主按钮、次按钮、图标按钮、危险按钮、禁用按钮。
- 图标家族：工具栏图标、菜单图标、状态图标、品牌图标。
- 文字家族：页面标题、面板标题、正文、菜单文字、辅助文字、快捷键文字、空状态文字。
- 输入家族：单行输入、搜索框、数值输入、选择器、颜色输入。
- 菜单家族：主菜单、二级菜单、更多菜单、右键菜单、导入导出菜单。
- 浮层家族：Tooltip、Popover、资源操作浮层、富文本工具栏。
- 面板家族：结构、主题、样式、搜索、大纲、卡片、属性面板。
- 对话框家族：普通确认、危险确认、导入、导出、设置、错误提示。
- 窗口家族：可拖动窗口、可缩放窗口、全屏视图、移动端抽屉。

- [ ] 每个家族的基线组件、样式入口和测试入口已经明确。
- [ ] 新成员已经登记所属家族，不允许以“特殊控件”为由脱离设计系统。
- [ ] 同一家族共享尺寸 token、文字 token、状态 token、层级规则和交互规则。
- [ ] 组件家族发生统一调整时，已批量验证全部成员，而不是只验证本次新增项。

## 5. 自动化门禁

### 5.1 定向测试

- [ ] 修改前新增测试可以准确失败。
- [ ] 失败原因与用户问题一致，不是无关环境错误。
- [ ] 完成最小实现后，定向测试通过。
- [ ] 相关领域测试通过。
- [ ] 没有删除或放宽原有断言来制造通过。
- [ ] 没有把核心回归用例改成 `skip`、`todo` 或条件永不满足。

### 6.3 图标、文字、快捷键与行项目对齐

> 菜单、工具栏、列表和面板中的每一行都必须使用同一套“列槽”布局。不得让不同图标各自占用不同宽度，也不得依靠空格、负边距或逐项微调来对齐。

推荐结构：`图标槽 + 文字槽 + 右侧信息槽 + 子菜单箭头槽`。没有图标、快捷键或箭头时仍保留对应空槽，保证所有行的起始位置一致。

- [ ] 每个行项目由独立的图标容器、文字容器、右侧信息容器和可选箭头容器组成，不把图标与文字混在同一个自由流动盒子中。
- [ ] 同一组件内所有图标槽宽度一致；有图标、复选框、单选标记或状态点时均占用同一列。
- [ ] 没有图标的行仍保留空图标槽，所有文字左边缘处于同一条垂直基准线上。
- [ ] 所有文字槽从同一水平位置开始，主菜单和二级菜单分别保持各自一致的文字起点。
- [ ] 快捷键、状态文字、数量或其他右侧信息使用独立列并统一右对齐，不挤压标题文字。
- [ ] 子菜单箭头使用独立固定槽；带快捷键和带箭头的行不会因为内容不同而改变文字起点。
- [ ] 同类行项目的高度、上下内边距、左右内边距和列间距一致。
- [ ] 图标外部盒子尺寸一致，图标在盒子中水平和垂直居中。
- [ ] SVG 图标使用统一的 CSS `width/height`、`viewBox` 规范、描边宽度、线帽和线连接风格。
- [ ] 不使用 Unicode 字符、不同字号字体图标或临时 emoji 替代正式 SVG 图标。
- [ ] 图标的“视觉大小”一致；细长、圆形或留白较大的图标可以在固定图标槽内部进行轻微光学校正，但不得改变图标槽尺寸或整行布局。
- [ ] 图标中心、文字行盒中心和右侧快捷键行盒中心位于同一水平中线上，不出现图标偏上、偏下或文字上下漂移。
- [ ] 所有标题文字使用统一字号、字重和行高；危险、禁用、选中状态只能改变颜色或状态装饰，不得改变字号、行高、内边距或列宽。
- [ ] 分隔线、分组标题和空状态遵循统一左右边界，不造成下一组文字突然左移或右移。
- [ ] 主菜单、二级菜单、顶部“更多”菜单、导入导出菜单和大纲右键菜单使用同一套行项目几何规则。
- [ ] 在浅色、深色、100% 至 200% 缩放及窄窗口下，图标和文字仍保持同列、同高、同中心线。
- [ ] E2E 使用 `getBoundingClientRect()` 检查同组行：图标槽宽度差不超过 1px、文字左边缘差不超过 1px、行高差不超过 1px、图标与文字中心线差不超过 1px、右侧快捷键右边缘差不超过 1px。
- [ ] 修改后提供带辅助参考线或叠加对比的截图，证明图标列、文字列和右侧列已经统一。

参考实现契约可以使用统一 Grid，而不是逐项 margin：

```css
.menu-item {
  display: grid;
  grid-template-columns:
    var(--menu-icon-slot)
    minmax(0, 1fr)
    max-content
    var(--menu-arrow-slot);
  align-items: center;
  column-gap: var(--menu-column-gap);
  min-height: var(--menu-row-height);
  padding-inline: var(--menu-padding-inline);
}

.menu-item__icon,
.menu-item__arrow {
  display: grid;
  place-items: center;
}
```

具体像素值应来自现有设计 token，不在单个菜单项中分别硬编码。

### 6.4 全局图标、按钮与文字系统

> 整个界面中的图标、按钮和文字必须来自统一系统。新增一个元素时，不能只保证它自身可用，还必须证明它与同类元素属于同一套视觉和交互语言。

#### 图标

- [ ] 所有业务图标来自统一图标注册表或统一资源目录，不在页面模板中临时手写重复语义的 SVG。
- [ ] 同一语义只保留一个正式图标；不得在顶部栏、右键菜单和对话框中各自使用不同图形表达同一动作。
- [ ] 同一使用场景的图标盒尺寸、实际图形尺寸、`viewBox`、描边宽度、线帽、圆角和 `currentColor` 规则一致。
- [ ] 图标按钮必须复用同类图标按钮组件，继承 hover、active、focus-visible、disabled、Tooltip 和 `aria-label`。
- [ ] 新图标在浅色、深色、禁用、危险和选中状态下都与同类图标具有一致对比度。
- [ ] 不得使用 Unicode、emoji、字体字符或临时图片替代已有线性 SVG 图标。
- [ ] 品牌图标与功能图标分开管理，功能图标不得擅自使用品牌色或独立视觉风格。

#### 按钮

- [ ] 新按钮必须选择现有按钮家族中的一个正式类型：主按钮、次按钮、轻量按钮、图标按钮、危险按钮或菜单按钮。
- [ ] 新按钮直接复用同类按钮的 DOM、CSS 类、尺寸 token、圆角、内边距、图标槽、文字槽和状态逻辑。
- [ ] 除需求明确要求外，不得创建新的按钮高度、字体、阴影、边框或颜色组合。
- [ ] 图标加文字按钮的图标与文字间距、中心线、点击区域和 loading/disabled 状态与同类一致。
- [ ] 只有图标的按钮必须有 Tooltip 和 `aria-label`，点击区域不得因为图形较小而缩水。
- [ ] 新按钮加入工具栏后，不得改变相邻按钮的行高、间距、分组边界或响应式收纳优先级。

#### 文字

- [ ] 页面标题、面板标题、分组标题、正文、菜单项、辅助文字、快捷键、状态文字和空状态使用既有文字 token。

- [ ] 同类文字的字号、字重、行高、颜色、截断、省略和换行规则一致。
- [ ] 同一动作在不同入口使用一致名称，不出现“删除当前”“删除节点”“移除当前”等无依据的文案漂移。
- [ ] 中文、英文、数字、快捷键和标点混排时基线稳定，不因字体回退导致行高变化。
- [ ] 禁用、危险、辅助状态只改变设计系统允许的颜色或装饰，不改变文字几何。

- [ ] 桌面侧栏、全屏面板、移动端抽屉之间使用同一内容组件，只替换壳层 variant，不复制三套业务实现。
- [ ] 1440、1024、768、390 宽度以及 100% 至 200% 缩放下不越界、不裁切关键按钮。

- [ ] 新组件与参考同类并排截图，比较标题栏、边框、圆角、阴影、背景、内边距、按钮和文字。

- [ ] 除明确 variant 差异外，容器圆角、边框宽度、标题栏高度、关闭按钮盒尺寸、正文内边距误差不超过 1px。
- [ ] 新组件不得新增只服务自己的全局样式规则、独立 `z-index` 或重复事件控制器。

推荐组件关系：

