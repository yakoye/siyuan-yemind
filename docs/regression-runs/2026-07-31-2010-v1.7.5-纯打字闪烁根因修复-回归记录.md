## 背景

v1.7.3/v1.7.4 均遗留一个未解决问题："纯打字（不拖动宽度）时仍偶发静态文字短暂可见"。用户随后自行用真实 SiYuan 客户端做了两轮关键调查：

1. 在真实 Chrome DevTools 里下断点，定位到 Quill `emitter.js` 的 `EVENTS.forEach` 全局事件分发，以及 SiYuan 内核 `common.*.js` 的 `Z.onmessage` WebSocket 处理——怀疑闪烁与这两处有关。经排查（见下文"排除的错误线索"），这条线索被证伪。
2. 录制了一段真实的 Chrome Performance trace（`Trace-20260731T195122.json.gz`，用户输入第一个字符后描述"文字向左上偏移，之后恢复正常"）并交给我分析，且明确说明"没有标注具体地方"，需要自行定位。

## 根因分析（trace 实证）

对 trace 做了完整解析（`traceEvents` 53440 条）。以文本输入事件为锚点定位：

| ts (us) | 事件 | 备注 |
|---|---|---|
| 222747011321 | keydown | 用户敲下第一个字符 |
| 222747014920 | textInput | |
| 222747016309 | input（dur=11us） | DOM input 事件很快完成 |
| **222747023688** | **RunTask 开始，dur=184330us（184ms！）** | 主线程被单个任务阻塞 184ms |
| 222747208070 | selectionchange | **恰好在上面这个 RunTask 结束后 52us 触发**——被整段阻塞 |

对这个 184ms 任务窗口内的子事件做统计，发现：

```
InvalidateLayout            374 次
ScheduleStyleRecalculation  373 次
UpdateLayoutTree            373 次
Layout                      371 次
LocalFrameView::performLayout 371 次
```

即单次按键触发了 **371 次强制同步布局（layout thrashing）**。CPU profile 采样进一步定位到耗时 180264us（几乎占满整个任务）的那一帧：

```
url: 'plugin:siyuan-yemind'
lineNumber: 95078, columnNumber: 41
```

对照已部署的构建产物与源码，精确定位到 `src/editor/RenderLifecycleCoordinator.ts:193`（`commitTextEdit()` 的实时编辑分支；该文件已在 v1.8.0 的画布文字编辑内核精简中被拆分删除，见 `docs/regression-runs/` 下 v1.8.0 相关记录）：

```ts
if (this.mindMap?.richText?.showTextEdit === true) {
  node.update?.();
  node.parent?.renderLine?.();
  node.renderLine?.(true);   // <- 根因：deep=true
  ...
}
```

`vendor/simple-mind-map-runtime` 的 `MindMapNode.js#renderLine(deep=false)` 无论 `deep` 是否为真都会重绘**自身**到直接子节点的连线；`deep` 参数唯一的作用，是额外递归调用每个子节点自己的 `renderLine(deep)`，从而波及所有子孙节点。而这条实时编辑快速路径里，`node.layout()`（`nodeLayout.js`）只重建被编辑节点自身的 SVG 内容，**不会**重新运行整棵子树的布局算法去移动子孙节点——也就是说子孙节点的位置根本没变，重绘它们的连线是纯粹的浪费，且开销随子树规模线性放大。

这精确解释了此前"小测试图从未复现、用户真实大文档必现"的现象：本次会话之前所有 E2E/CDP 复现尝试都用的是节点数很少的测试图，子树递归的浪费量太小，不足以产生可感知的阻塞；用户真实文档中被编辑节点带有较大子树，单次按键触发 184ms 阻塞，足够丢十几帧，表现为"文字向左上偏移，之后恢复正常"。

## 排除的错误线索

用户提供的两组 DevTools 断点线索（Quill `emitter.js` 的 `EVENTS.forEach`，SiYuan 内核 `Z.onmessage`）以及随后发现的 `data/storage/petal/siyuan-kmind-zen/` 存储目录，一度被误判为"另一个正在运行的第三方插件与 YeMind 抢事件"。经核实：

- `data/plugins/` 下确实没有 `siyuan-kmind-zen` 目录，`petals.json` 已启用插件列表里也没有它。
- 但 `tests/suites/contracts-compatibility/v081PluginIdentity.suite.ts` 明确证明：**YeMind 自己在更早阶段就叫 `siyuan-kmind-zen`（`KMind Zen`）**，该测试专门守护"绝不能回退到旧名字"（检查 `src/plugin/YeMindZenPlugin.ts` 不存在、文档不含 `KMind Zen`/`siyuan-kmind-zen`）。
- 因此 `data/storage/petal/siyuan-kmind-zen/`、`conf.json` 里的 `siyuan-kmind-zenDock`、`local.json` 里的 `kmind-zen:*` 键，都是重命名前遗留的旧存储痕迹，不是独立插件在抢事件。

已在上面的 CHANGELOG 中如实记录这条被推翻的线索，避免后续误导。

## 对应修复

`src/editor/RenderLifecycleCoordinator.ts`：`commitTextEdit()` 实时编辑分支的 `node.renderLine?.(true)` 改为 `node.renderLine?.()`，去掉不必要的深度递归；保留对 `node.parent?.renderLine?.()`（父节点自身到本节点的连线）的调用不变。

## 新增失败测试

`tests/suites/rich-text-editing/v151RenderLifecycle.suite.ts` 新增用例：构造"编辑节点 → 子节点 → 孙节点"三层结构，`renderLine` mock 按真实 `MindMapNode.js` 的契约实现（`deep` 为真时才递归调子节点），断言单次 `scheduleTextEdit` 提交后：

- 被编辑节点自身的 `renderLine` 恰好调用一次；
- 子节点、孙节点的 `renderLine` **都不应被调用**。

已确认此测试在修复前失败（子节点 `renderLine` 实际被调用了 1 次，因为旧代码传入 `deep=true` 触发了递归），修复后通过。同时更新了同文件中原有的 `keeps an open editor on one live SVG node instead of replacing the whole tree` 用例，把断言从 `toHaveBeenCalledWith(true)` 改为 `toHaveBeenCalledWith()`，使其不再把旧的 `deep=true` 行为当作预期正确结果继续锁定。
