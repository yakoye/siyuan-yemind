## 背景

v1.7.5 发布后用户反馈"输入文字抖动"依然存在，并自行做了更严谨的复核：

1. 拆解了 v1.7.5 引用的第一份 trace（`Trace-20260731T195122.json.gz`），指出上一版把 16ms 窗口和 `startPlacementMonitor` 的 `tick()`（`reconcileEditorPlacement`/`normalizeEditorPlacement`/`applyEditorGeometry`）判定为"制造错位再修回来"的两段逻辑，并给出了完整的建议修复方向。
2. 额外录制并解析了第二份 trace（`Trace-20260731T203417.json.gz`，34,318 条事件），且**这次导图里只有一个节点、没有子节点**——直接排除了"子树递归"作为主要根因的可能性。
3. 对比两份 trace 的 CPU 采样次数：

   | 函数 | Trace 1 采样数 | Trace 2 采样数 |
   |---|---:|---:|
   | `commitTextEdit` | 1,964 | 3,573 |
   | `createTextNode` | 1,668 | 2,733 |
   | `measureText` | 1,534 | 2,359 |
   | `layout` | 282 | 808 |
   | `renderLine` | 1 | 3 |

   用户由此指出：v1.7.5 把约 180ms 耗时几乎全部归因于 `node.renderLine(true)`，是**单帧栈归因错误/过度归因**——真正占大头的是 `createTextNode`/`measureText`。

## 复核结论：接受更正

对照 `vendor/simple-mind-map-runtime/src/core/render/node/nodeCreateContents.js` 的 `createTextNode()`（[nodeCreateContents.js:259-280](../../vendor/simple-mind-map-runtime/src/core/render/node/nodeCreateContents.js)）：

```js
textArr.forEach((item, index) => {
  let arr = item.split('')   // 按单个字符拆分
  let lines = []
  let line = []
  while (arr.length) {
    let str = arr.shift()
    let text = [...line, str].join('')
    if (measureText(text, this.style).width <= maxWidth) {   // 每个字符都测量一次
      line.push(str)
    } else {
      lines.push(line.join(''))
      line = [str]
    }
  }
  ...
})
```

`measureText(text, style)`（[nodeCreateContents.js:17-23](../../vendor/simple-mind-map-runtime/src/core/render/node/nodeCreateContents.js)）每次调用都新建一个 SVG `<g>`+`<text>` 元素并调用 `g.bbox()`（内部走原生 `getBBox()`，强制同步布局）。也就是说：**自动换行的逐字符探测循环，每敲一个字符就会对整段文字重新做一次"从头到尾、每个字符一次 `getBBox()`"的测量**——这是文本长度的线性次强制布局，与子树、子节点数量完全无关。这精确解释了为什么"只有一个节点"依然复现：两次 trace 的强制 `Layout` 次数（371 次 / 268 次）都远超"重画几条连线"能产生的量级，且与 `renderLine` 的极低采样数（1~3 次）相印证。

而 `commitTextEdit()`（实时编辑分支）在**每一次提交**（即每次 `scheduleTextEdit` 触发的动画帧）都会调用一次 `node.createTextNode(measurementText)` 做完整重测量。第二份 trace 的调度栈进一步显示：

```text
onCompositionUpdate（Quill 自身的输入法组合处理）
  → text-change（source: user）
    → node_text_edit_change
      → scheduleTextEdit
```

即中文输入法**每次 `compositionupdate`（候选更新，不是 `compositionend`）**，Quill 自身都会同步内部 Delta 并触发 `text-change`，YeMind 的监听器（[YeMindRichText.ts:1114](../../src/editor/YeMindRichText.ts)）对此没有做任何节流区分，直接调度一次完整提交。这意味着一次中文候选输入的多次 `compositionupdate` 会各自触发一次完整的高成本测量。

v1.7.5 的 `renderLine(true) → renderLine()` 改动本身**没有错**（它确实消除了子树场景下的一部分浪费，且已有回归测试保护），予以保留；但它不是本次症状的主要根因，CHANGELOG 与相关文档已做更正说明。

## 修复方案

没有直接改写 `vendor/simple-mind-map-runtime` 的测量算法（风险高，且需要走"补丁/适配层"流程另行评估），而是在调用方（`src/editor/RenderLifecycleCoordinator.ts`，该文件已在 v1.8.0 的画布文字编辑内核精简中被拆分删除）给实时编辑提交本身加防抖：

- 新增 `RenderLifecycleTimer` 接口（`request(callback, delayMs)`/`cancel(id)`），默认实现基于 `window.setTimeout`/`clearTimeout`，与既有 `RenderLifecycleScheduler`（rAF）的可注入测试模式保持一致。
- `scheduleTextEdit()` 对非 `paste` 原因的调用，不再直接排一次动画帧，而是先启动一个 160ms 的防抖定时器；定时器到期后才进入原有的 rAF 调度并执行 `commitTextEdit()`。连续的按键/组合更新会不断取消并重启这个定时器，直到输入停顿 160ms 才真正提交一次。
- `flushPendingTextEdit()`（编辑器关闭/失焦时调用）**不受防抖影响**——它直接读取已经同步保存的 `this.pending`（在 `scheduleTextEdit()` 里同步赋值，不等定时器），立即同步提交，保证退出编辑不会因为还在防抖窗口内而丢字。
- `invalidate()`/`destroy()` 同步清理防抖定时器与已排的动画帧，避免节点被删除/替换后残留的防抖仍然触发。
- `paste` 原因的提交保持原有的"立即提交、不进防抖"行为不变。

节点实时增长边框、连线跟随等既有功能不受影响，只是从"每个字符都重新测量一次"变成"停顿约 160ms 后测量一次"。

## 新增回归测试

`tests/suites/rich-text-editing/v151RenderLifecycle.suite.ts` 新增两个用例：

1. **"coalesces a burst of rapid keystrokes / IME composition updates into one commit after the debounce window..."**：连续调用 4 次 `scheduleTextEdit`（模拟 `P`→`PC`→`PCI`→`PCIe` 的连续输入/组合更新），断言在防抖定时器和动画帧都触发之前 `createTextNode` 一次都不应被调用；两者都触发后，`createTextNode` 恰好被调用一次，且使用的是最后一次（`'PCIe'`）的文本，不是中间任何一次。
2. **"flushes the latest edit immediately when the editor closes mid-debounce..."**：安排一次编辑后立即调用 `flushPendingTextEdit()`（不触发防抖定时器），断言 `createTextNode` 已经以最新文本被同步调用——验证关闭编辑器时不会因为还在防抖窗口内而丢失最后输入的内容。

同时更新了原有 8 个用例的 `RenderLifecycleCoordinator` 构造调用，注入一个"同步触发"的假定时器（`syncTimer`），使它们在引入防抖后仍保持原来"单帧同步提交"的语义和断言不变。
