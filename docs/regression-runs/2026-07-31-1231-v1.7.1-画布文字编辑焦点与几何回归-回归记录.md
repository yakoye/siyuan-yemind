## 复现方式

1. 打开 YeMind 独立网页版（`npm run dev:web`），或思源插件中的 YeMind 导图。
2. 双击一个节点进入文字编辑。
3. 逐字符真实键入（而非一次性 `fill()`）。

自动化复现（避免依赖特定字体/缩放/主题才能触发）：在编辑会话进入 `active` 阶段后，将 Quill 编辑器 DOM 的 `getBoundingClientRect()` 强制偏移 5px（模拟字体度量、缩放或自定义宽度节点造成的几何漂移），再继续真实逐字符输入，观察编辑层是否被隐藏、失焦。见 `tests/e2e/web-rich-text-outline.spec.ts` 中 `a transient editor/target geometry mismatch during typing must not hide or unfocus an already-active canvas editor`。

## 根因分析

1. `RenderLifecycleCoordinator.commitTextEdit()`（`src/editor/RenderLifecycleCoordinator.ts`）在每次按键触发的渲染事务中都会调用 `node.createTextNode()` + `node.layout()` + `node.update()` + `node.renderLine()` 重建节点的 SVG 静态文字，然后调用 `richText.updateTextEditNode()`。
2. `YeMindRichText.commitOpeningPlacement()`（`src/editor/YeMindRichText.ts`）在每次这样的提交中都会用 `editorContentRectAligned()` 重新比较 Quill 编辑器 DOM 矩形与刚重建的 SVG 目标矩形（容差 1.5px），并**无条件**把比较结果写入 `host.dataset.yemindGeometryReady`。
3. `src/styles/index.css` 中存在规则：`.ymz-editor .smm-richtext-node-edit-wrap:not([data-yemind-geometry-ready="true"]){visibility:hidden!important}`。只要上一步把该属性写回 `'false'`，编辑层立即被 CSS 强制隐藏。
4. Chromium 无法让一个 `visibility:hidden` 的元素保持 DOM 焦点；编辑层被隐藏的同一时刻，焦点会跳回画布容器（或 `document.body`），导致此后所有按键都不再进入 Quill，表现为“第二个字符无法输入”。
5. 同一个 `data-yemind-geometry-ready` 属性也是 `canvasRichTextVisibility.ts` 判断是否隐藏节点旧 SVG 静态文字层的依据（`replacementEditorReady()`）。编辑层被误判为未就绪的同一帧，刚刚用最新文字重建的 SVG 静态文字层不会被隐藏，与（此时已不可见但仍持有旧内容或正在过渡的）Quill 层短暂并存，视觉上呈现为“重影/加粗”。
6. 触发条件：会话已经进入 `active`（首次对齐、编辑层已可见可编辑）之后，任意一次按键导致的重新对齐检查出现哪怕极小的漂移（字体度量、系统缩放、自定义宽度节点、居中/右对齐文本随文字变长而左边界变化等），都会把已经处于活跃状态的编辑层重新打回“未就绪”，而不是像 1.6.1 版本引入“一次性原子换手”设计时所期望的那样保持稳定。这与 `ARCHITECTURE.md`、`CHANGELOG.md` 中记录的既有设计意图（“Kept the static SVG text visible until the replacement editor has both final geometry and meaningful content, then performed one atomic text-layer handoff”）相悖——换手本应只发生一次，而不是随每次按键反复评估、可能反悔。
7. 次生缺陷（同一条排查路径中发现）：`InsertedNodeEditCoordinator` 创建的新节点在 `focus(0)` 时用 `Quill.sources.SILENT` 静默选中全部文字，因此 Quill 自身的 `selection-change` 从不会为这次初始选中触发；而 `initQuillEditor()` 里“吞掉插入节点的第一次 selection-change 并复位 `isInserting`”的一次性守卫，实际吞掉的是用户之后第一次**真实**选中操作，导致新建节点打字后首次选中文字不显示格式工具栏，需要再选一次才生效。

## 对应修复

- `src/editor/CanvasEditSessionCoordinator.ts`：`markEditorReady()` 一旦会话已进入 `'active'` 阶段即直接返回当前快照，不再因为某一帧的重新对齐失败而把阶段打回 `'opening'`。
- `src/editor/YeMindRichText.ts`：`commitOpeningPlacement()` 在会话已经处于 `active` 时，把 `host.dataset.yemindGeometryReady` 钉在 `'true'`，不再随当帧对齐结果波动；节点外框/编辑层的位置仍然通过 `applyEditorGeometry`/`normalizeEditorPlacement` 在每次提交中正常更新，只是可见性/焦点闸门不再倒退。
- `src/editor/YeMindRichText.ts`：`commitOpeningPlacement()` 完成“是否自动展示工具栏”的一次性判定后立即复位 `this.isInserting = false`，避免用户在新建节点上的第一次真实文字选中被静默吞掉。
- 均为最小侵入修改，未改变 `RenderLifecycleCoordinator` 的重建时机、未关闭实时编辑/富文本/大纲同步，未使用轮询式强制刷新或反复抢焦点掩盖问题。

## 新增失败测试（先失败后通过）

新增于 `tests/e2e/web-rich-text-outline.spec.ts`（均使用真实 `pressSequentially`/原生 `compositionstart`/`compositionupdate`/`compositionend`/`input` 事件，而非 `.fill()`）：

1. `canvas text edit accepts real sequential English and digit keystrokes without losing focus or ghosting`
2. `canvas text edit keeps IME composition uncommitted until compositionend and does not trigger structural shortcuts mid-composition`
3. `a second canvas edit session on a different node accepts continuous typing after switching from the first node`
4. `an existing text node accepts continuous retyping after real selection and deletion`
5. `real per-character canvas typing commits exactly once and undo/redo restore it in one step`
6. `a transient editor/target geometry mismatch during typing must not hide or unfocus an already-active canvas editor`（**根因定位测试**：修复前失败，报错 `data-yemind-geometry-ready` 从 `"true"` 回退为 `"false"`；修复后通过）

修复前执行：测试 6 失败（编辑层被隐藏、失焦，与用户报告症状一致）；测试 3 也失败（第二会话工具栏不出现，对应上文“次生缺陷”）。修复后：全部 6 项通过，且未削弱任何断言。

## 架构审查结论摘要

详见交付说明；简要结论：

- 已确认并修复：画布文字编辑期间几何对齐失败导致编辑层被反复隐藏/失焦（本次主因）；新建节点后首次文字选中不显示工具栏（次生）。
- 已确认但本次不适合修改：`initQuillEditor()` 在每次进入编辑时都重新创建 Quill 实例而非复用（有 CPU/GC 浪费，但经核实 Quill 内部 `document` 级监听是模块级单例并以容器节点为键正确复用，不构成持续增长的内存泄漏；修复需要改造“打开编辑=装载初始内容”为“复用实例+`setContents()`”，改动面更大，留待后续独立处理）。
- 尚未确认：真实思源宿主（而非独立网页版）在自定义字体、非 100% 系统缩放或极端窄宽节点下是否存在额外的一次性对齐失败模式；本次修复已让该失败模式在发生时不再影响可用性，但根本的“对齐为何漂移”仍可能因具体宿主环境而异，建议后续用真实思源客户端采集更多现场数据。
