## 用户报告问题

v1.7.2 部署后，用户报告以下现象仍未解决：

1. 双击编辑，随便输入，整个节点文字来回跳。
2. 文字全选后拖动节点宽度，能看到两层文字重影（用户提供截图：节点压缩到最小时，可见一行完整文字和另一行按极窄宽度逐字换行的文字同时叠在一起）。

## 本次调查方式：真实思源实机调试

前两轮（v1.7.1、v1.7.2）均只能在独立网页版中复现和验证，无法确认真实思源客户端环境下的表现。本轮改用 `SiYuan.exe --remote-debugging-port=9222 --remote-allow-origins=*` 启动真实桌面客户端，通过 Chrome DevTools Protocol（WebSocket JSON-RPC，`Runtime.evaluate`、`Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`、`Input.insertText`）直接向真实渲染进程注入真实指针点击、真实按键和真实文本插入，在用户的真实工作区（"测试导图"等既有文件）中复现问题。

**过程中的数据安全处置**：所有复现均在新建的一次性测试子节点上进行，验证后立即通过应用自身的删除/撤销操作清理，并核对节点总数、"新节点"占位符数量、以及关键既有节点（如 "AER"）在清理前后完全一致，同时确认应用内"已保存"状态。未对用户原有节点内容做任何增删改。

## 根因分析

### 现象 2（宽度拖动重影）—— 已确认并修复

`vendor/simple-mind-map-runtime/src/core/render/node/nodeModifyWidth.js` 的 `preserveLiveTextData()`/`reconcilePaintedDom()` 在宽度拖动时**刻意复用**已绘制的静态文字 DOM 节点（避免整段替换造成的空白/闪烁帧），但其 `copyDomAttributes()` 会把新测量出的节点的**完整 `style` 属性**复制到被复用的旧节点上。YeMind 通过 `wrapper.style.setProperty('visibility','hidden','important')` 隐藏编辑中节点的静态 SVG 文字，这个隐藏状态正是写在同一个 `style` 属性里——于是每次宽度拖动的鼠标移动帧，都会把"隐藏"覆盖掉，使静态文字重新可见，与正在编辑的 Quill 层同时显示，形成重影。

已通过真实指针拖动（`Input.dispatchMouseEvent` 连续 25 帧、"选中文字→拖动宽度手柄"）复现：`bothVisible` 一度达到监测帧数的 100%（812/812）。

同时发现一个更严重的伴生问题：宽度拖动的 DOM 复用与画布同时进行的逐字符编辑提交（`RenderLifecycleCoordinator.commitTextEdit`）之间存在竞态，可能导致**整个外层 SVG 文字组被复制**而不是复用，产生一个"孤儿"文字组——不再被 `node._textData` 引用、永远不会被隐藏或移除，永久显示为节点的第二份重复标签（复现时一度观察到 `staticCount` 高达 34）。

### 对应修复

- `src/editor/liveNodeWidthLayout.ts`：`LiveNodeWidthLayoutController.synchronizeEditingSurface()` 在编辑会话激活期间的每个拖动动画帧，除了原有的 `updateTextEditNode()` 之外，追加调用 `synchronizeCanvasRichTextVisibility(this.map)`，每帧重新断言隐藏状态。
- `src/editor/canvasRichTextVisibility.ts`：新增 `removeOrphanedStaticTextLayers()`，以节点自身稳定的顶层 SVG 组（`node.group.node`，节点生命周期内不变）为根，扫描并移除不属于当前 `node._textData` 引用范围内的 `.smm-text-node-wrap`/`.smm-richtext-node-wrap` 孤儿元素。已验证多行节点的合法多行内容（同属一个被跟踪的外层组）不受影响。

修复后重新用相同的真实拖动序列复现：孤儿累积由最高 34 个降为稳定的 1 个（`maxStaticCount` 恒为 1）。

### 现象 1（连续输入时文字跳动）—— 尝试的修复已回退，问题未解决

调查中最初怀疑一个几何问题：`src/editor/richTextGeometry.ts` 的 `logicalTextRect()` 会无条件用 `data-width`/`data-height` 属性反推一个"逻辑矩形"。`createTextNode()` 在测量宽度达到 `textAutoWrapWidth`（自动换行边界）时会把 `data-width` 钳制到该边界值，这个钳制值可能与浏览器实际绘制的字形宽度不一致。**曾尝试的修复**：让 `logicalTextRect()` 仅在 `node.hasCustomWidth()` 为真时才应用该"逻辑矩形"修正。

**该修复已在本轮回退**。完整 Playwright 回归套件（`npx playwright test`）跑出 4 个失败，全部指向同一根因：`logicalTextRect()` 的"逻辑矩形"修正对**居中/右对齐的多行节点**同样是必要的（用于把编辑层对齐到统一宽度框的居中位置），并非仅服务于自定义宽度节点。加上门控后，普通居中对齐节点（包括默认根节点）打开编辑时永远无法通过 `editorContentRectAligned` 的对齐检查，会话永远停在 `opening` 阶段，编辑层永久保持 `visibility:hidden`——比原问题更严重的回归。已确认回退后 4 个失败全部恢复通过。

同时，用真实思源实机重新测试**纯打字、不拖动宽度**场景（该 `hasCustomWidth` 修复生效期间）发现：即使加上该门控，静态 SVG 文字层与 Quill 编辑层同时可见的帧仍然存在（约 50% 采样帧）——说明这个门控从一开始就没有对准"文字跳动"的真正根因。追踪 `synchronizeCanvasRichTextVisibility()` 内部关键判定变量（`session.phase`、`geometryReady`、`contentReady`、`replacementEditorReady()` 返回值）发现：这些条件在被采样的每一次调用中都正确为"就绪"，理应执行隐藏——但实际渲染结果仍会出现短暂的双层可见帧。受时间限制，未能在本轮定位到这个残余问题的确切触发机制。

**这是本次唯一未能解决的问题，如实记录，不作虚假的"已修复"声明；相关的错误尝试已完整回退，不遗留在最终代码或文档中。**

## 新增回归测试

- `tests/suites/user-regressions/v0917UserReportedInteractionRegression.suite.ts`：新增"re-hides the static SVG text on every width-drag frame even after upstream reconciliation clears its style attribute"，直接模拟 `copyDomAttributes` 的 style 属性清空效果，验证控制器能在同一拖动帧内重新隐藏。
