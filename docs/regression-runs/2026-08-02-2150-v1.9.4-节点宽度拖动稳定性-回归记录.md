## 2. 复现证据与根因

输入 Trace：`C:/Users/color/Downloads/Trace-20260802T205636.json.gz`。

用户操作为拖动节点右侧宽度手柄。旧实现每个 `mousemove` 都执行 `this.reRender(['text'])`；上游 `nodeLayout.layout()` 随后调用 `group.clear()`，导致当前 SVG 文字子树和 `foreignObject` 在每一帧被移除并新建。Chromium/Electron 因此可能合成出文字位于左上角、文字消失或恢复原位的中间帧。

新增逐帧回归在修复前记录到：24 个拖动步发生 24 次文字祖先移除。该结果证明问题来自每帧重建文字 DOM，不是坐标差 1px、延时不足或思源宿主性能不足。

## 3. 修复方式

- 修改 `vendor/simple-mind-map-runtime/src/core/render/node/nodeModifyWidth.js`。
- 拖动期间把新测量得到的文字内容和几何增量同步到当前 live 文字子树，保持文字组和 `foreignObject` DOM 身份不变。
- 保留现有布局的 `x`、`y`、`transform`，同步节点外形、hover 区域和展开占位，不在鼠标移动期间清空并重建文字树。
- 鼠标释放时先把当前节点数据写入渲染快照，再执行一次上游规范 `mindMap.render()`；最终布局与连线仍走 simple-mind-map 标准提交路径，但不再把拖动期间已经正确绘制的文字子树拆除重建。
- 没有新增定时器、坐标补偿、覆盖层或新的 Coordinator。
- `UPSTREAM_BASELINE.json` 明确登记这一处有 Trace 和回归测试支持的上游分支差异。

## 5. 2026-08-02 追加验收：释放帧与新节点首帧

### 5.1 原验收缺口

- 原宽度拖动用例在 `page.mouse.up()` 之前停止采样，只能证明拖动过程稳定，不能证明松手提交帧稳定。
- 原 Tab/Enter/+ 用例只检查编辑器 DOM 的 `innerText`，即使 SVG 首个可见帧没有任何可绘制字形也会通过。

### 5.2 确定性根因与最小修复

- 宽度释放：拖动期间 live 文字子树已经是最终内容，但 `mouseup` 后节点快照仍是旧值，最终 `render()` 再次重建内容子树。现在在提交前同步 `nodeDataSnapshot`，避免无意义的内容重建，仍保留上游布局提交。
- 新节点首帧：YeMind 插入节点时只传递了 pristine 标记，未覆盖 simple-mind-map 默认参数中的 `richText: true`，导致新节点首次以 `foreignObject/div` 挂载，编辑器接管前出现空白帧。现在由 YeMind 命令层明确传递 `richText: false`；用户真正编辑并提交后，仍由既有流程按需升级富文本。
- 没有修改 simple-mind-map 的通用 `Render.js` 插入规则，避免扩大上游分支差异。

### 5.3 新增硬门禁

- 宽度拖动：记录每帧 shape/text 几何、文字 DOM 身份和 detach 次数；`mouseup` 前后不得出现超过 1px 的几何跳变，不得更换文字 DOM，不得 detach。
- Tab、Enter、+：从新 SVG 节点第一次挂载开始逐帧检查；每个可见帧必须满足“静态 SVG 字形已绘制”或“可见编辑器字形已绘制”，首个静态文字元素必须为 SVG `<text>`。
- 所有定向用例使用 `--retries=0`，不使用等待、重试或概率容差掩盖失败。
